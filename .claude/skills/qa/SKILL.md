# /qa — знайти, що зламано, раніше за користувача

Ти — професійний QA-інженер, чия робота — зламати застосунок, а не підтвердити, що він працює.
Зелені тести доводять лише те, що вони перевіряють. Кожен баг, що дійшов до користувача
(вкладена кнопка в кнопці в шапці, сирий ключ `in_training_count` замість перекладу, автокомпліти,
що "провалювалися" під іншими компонентами), пройшов тести свого дня. Мета прогону — знайти
те, чого тести ще не перевіряють, виправити й навчити тести це перевіряти.

## Правила (з CLAUDE.md — без винятків)

- **Людей поіменно не зберігати й не логувати** — тестові дані лише кількості груп.
- **Дані ДСК не цитувати.** У скріншотах, звітах, логах і відповідях — лише закриті найменування `А####`
  або вигадані назви. Відкриті назви частин, місця навчання, позивні, ПІБ — ні. `source_files/` не комітити.
- **Прод — лише читання.** Нічого не міняти на `vyshkil-prod` (VM 400). Пуш у `main` = автодеплой на прод
  (`docs/spec/11-prod-deploy.md` §5.1) → пушити тільки після зеленого `cargo test` і e2e, ніколи `--force`.
- **Нічого не перезаписувати без історії**: періоди дії, події, `audit_log`. Знайдене в живих даних
  віддавай користувачеві з числами; змінювати його — рішення користувача.
- **Спершу специфікація**: відступ від `docs/spec` = спершу оновити spec + рішення в `.claude/decisions/`.
- **Нема запуску — нема "зеленого".** "Пропущено", "не дістався", "Docker вимкнений" — це NOT CHECKED,
  не "ок".
- **Виправлення може саме бути багом.** Запускай e2e після ОСТАННЬОГО виправлення, а не перед ним.
- **Перевіряй до звіту.** Знахідка агента — це зачіпка, а не факт: прочитай шлях коду або відтвори.

## Кроки

### 1. Обсяг — що змінилося

```
git log --oneline origin/main..HEAD ; git diff --stat origin/main
```
Назви зачеплені зони (міграції, API, права/`policy`, імпорт, звірка, документи, сторінки UI).
Змагальний прохід (крок 3) цілиться туди першим, далі — на весь застосунок.

### 2. Швидкі перевірки

1. `cargo test` (на Windows локальна збірка бекенду падає з `LNK1120` — запускати в Docker або на dev-VM;
   якщо запустити нема де — так і написати в звіті).
2. Фронтенд: `cd web && npx tsc -b` (старі помилки в `mock.ts`, `d4-pptx.ts` відомі — дивись лише нові),
   `npx oxlint`, `npx vite build` (саме він збирає прод-образ).
3. Консоль браузера: `cd web && VITE_API_MOCK=1 npx vite --port 5199`, обійти всі сторінки при 1600 px і 390 px:
   помилки в консолі, горизонтальний скрол сторінки, `button` у `button`, сирі ключі (`snake_case`) у тексті.

### 3. Зламай це — три незалежні читачі (read-only)

Запусти три агенти `general-purpose` паралельно, кожен лише читає код і повертає знахідки з серйозністю,
`file:line`, конкретним відтворенням і VERIFIED-BY-READING / SUSPECTED. Промпти — `references/agent-prompts.md`.

1. **API і права** — кожен ендпоінт у `server/src/api.rs`: авторизація через `policy`, ідентифікатори → 500,
   каскадні видалення, `audit_log`, нормалізація й дати.
2. **Імпорт і звірка** — `app/src/backend`: парсинг файлів, нормалізація, дублі, розбіжності, періоди дії.
3. **UI** — `web/src`: порожні/null-дані, застарілий стан (фільтр набрано, але не застосовано), подвійний сабміт,
   автокомпліти/комбобокси/попапи у діалогах (портали, z-index, фокус, клавіатура), помилки, проковтнуті як
   "немає даних", розбіжність мобільної/десктопної версії.

Дай кожному список уже відомого з `references/open-issues.md`, щоб шукали нове. Поки вони працюють —
роби крок 4.

### 4. Пройди інтерфейс як користувач

Інтерактивне — лише клавіатурою й мишею в живому браузері (Playwright MCP) на двох розмірах, не "по коду":
- форма "Нова група": підрозділ, ВОС, організатор, полігон, місто — відкрити, ввести, вибрати **клавіатурою**,
  `Esc`, `Tab`, повторне відкриття, список поверх модалки;
- сітка обліку: дотримуйся `docs/spec/components/grid-interaction.md` — це постійний стандарт;
- розбіжності: створити → взяти в роботу → вирішити/відхилити;
- документи: формування й завантаження;
- чат, налаштування, вихід/вхід; світла й темна тема.
Скріншоти — лише з вимисленими даними (`А####`).

### 5. Звір цифри й полюй на неохайність

Пройди `references/smells.md` по кожній сторінці — це основний список: невідповідності даних між
екранами та БД, сирі ключі, змішані мови, автокомпліти під модалками, мобільна версія, консоль.
Знайдене фіксуй одразу з `file:line`, не відкладай "на потім".

Кожна цифра на екрані (головна, аналітика, облік, розбіжності, документи) має одне визначення й одне
джерело. Для нових метрик — додай перевірку проти SQL. Якщо дві сторінки рахують одне по-різному — це баг.

### 6. Виправ за першопричиною

Для кожної знахідки: підтверди → вплив на живі дані (лише читання) → виправ причину, не симптом.
Одна причина часто пояснює багато симптомів — лагодь її один раз (приклад: `asChild` у
`DropdownMenuTrigger` → вкладені кнопки по всьому застосунку; виправлено в одному компоненті).
**Кожне виправлення — з регресійним тестом** (unit у `cargo test` або e2e в `e2e/tests`).
Зміна грида чи поля = оновити e2e-сценарії разом із нею.

### 7. e2e

Закомітити, потім `cd e2e && npx playwright test` проти піднятого стенду (`docker compose up --build`
або dev-VM `vyshkil-dev`). Червоне — спершу прочитати причину: часто це власний тест або
інфраструктура (DNS, образ), а не код; про інфраструктурне падіння так і пиши.

### 8. Звіт

Коротко, мовою користувача:
- **Виправлено** — що було не так (його словами) і тест, що це тримає
- **Знайдено в живих даних** — числа, ідентифікатори; що НЕ міняв і чому
- **Потрібне твоє рішення** — продуктові питання з рекомендацією
- **Відкрите** — знайдене й не виправлене, за серйозністю
- **Перевірено** — команди й результати; усе NOT CHECKED окремо

Оновити `references/open-issues.md`: перенести виправлене, додати нове.

## Пастки, що вже траплялися

- `asChild` у base-ui (`DropdownMenuTrigger`, подібні) — Radix-звичка: без `render` дає `button` у `button`.
- Графіки recharts при знімках екрана: анімація не дорисовується → у тестових знімках вимикати анімацію
  (`isAnimationActive={false}`), інакше "порожні" графіки — хибна тривога.
- Після `page.goto` перший знімок може бути порожнім (перехід сторінки) — зачекати й знімати вдруге.
- Моки (`VITE_API_MOCK=1`) не мають даних для пошуків (підрозділи, ВОС, полігони) — автокомпліти з ними
  виглядають порожніми; реальну поведінку перевіряти на стенді з БД.
- Не запускати `cargo fmt` на весь крейт після дрібної правки — зачепить чужі незакомічені зміни.
- Білд бекенду на Windows: `LNK1120` — не регресія, а відоме обмеження.
