# Власна стильова система замість Tailwind/UnoCSS — архітектура (Фаза 0)

## Контекст

`app/style/main.css` (~765 рядків, BEM, частина кольорів захардкоджена) + 89 інлайн `style=` у
компонентах — зросло органічно за 5 етапів без єдиної системи токенів. Палітра (виміряно зі
striy.pp.ua, `.claude/decisions/ui-visual-style-source.md`) правильна й лишається базою — питання
лише в тому, ЯК доставляти й перевіряти стилі далі.

## Розглянуті альтернативи

1. **Tailwind CSS (через `leptos-tailwind`/Vite)** — запропоновано іншою моделлю, відхилено:
   зовнішній бінарник/Node.js у стеку (00-agent-brief.md: заборонено), класи — неперевірені рядки
   компілятором. Contra-аргумент "за" (Tailwind CLI сам офлайн-здатний) розглянуто й визнано
   недостатнім — бінарник поза `cargo` все одно чужорідний цьому стеку, і типобезпеки не додає.
2. **UnoCSS** — та сама проблема (Node/зовнішній інструмент), плюс "on-demand"-парсинг рядків
   класів ще менш прозорий для Rust-компілятора.
3. **Чистий BEM (поточний стан)** — нуль нових залежностей, але жодної типобезпеки: токен-дрейф
   (кольори, вписані як hex у різних місцях — уже сталось, задача явно про це каже) не ловить
   ніщо, крім людської уваги.
4. **Власний рушій: Rust-токени + CSS-генератор + `cx!`-проц-макро** — обрано.

## Чому обрано (4)

- Жодної зовнішньої залежності поза `cargo` (офлайн, без Node) — відповідає жорсткому правилу
  проєкту.
- Друкарська помилка в класі — помилка КОМПІЛЯЦІЇ, не мовчазний рядок без стилю (перевірено
  Фазою 0 — реальний `cx!("p33")` дає підказку "може, ви мали на увазі «p3»?").
- Токени як Rust-дані — той самий крейт, що генерує CSS, ЖИВИТЬ і контраст-тест (Фаза 1), і
  архітектурний тест "жодного hex поза `style`" (Фаза 4) — одне джерело істини, не три
  паралельні (CSS-файл, документація, тест).

## Ціна

- Новий крейт (`style`) + проц-макро-крейт (`style_macros`) у workspace — 2 додаткові Cargo.toml,
  трохи довша збірка (виміряно: ~3с холодний `cargo check` обох, не проблема).
- **Немає єдиного джерела граматики між `style` і `style_macros` без циклу залежностей** (якщо
  `style` реекспортує `cx!` для ергономіки `style::cx!`, то `style` → `style_macros` і водночас
  `style_macros` → `style` для читання `ATOMS` — цикл, Cargo це забороняє). Фаза 0 обійшла
  дублюванням 20-атомної таблиці в обох крейтах (задокументовано в коді). **Фаза 1 має вирішити
  насправді**: спільний дата-файл через `include!()` (обидва крейти читають той самий фізичний
  `.rs`-файл з даними, жоден не залежить від іншого) або третій крейт `style_core` (лише дані, без
  логіки, обидва `style` і `style_macros` залежать від НЬОГО, не один від одного).
- **Постачання CSS вимагає ручного кроку** (§9 `08-style-system.md`) — `cargo-leptos` не підхопить
  згенерований файл автоматично (build.rs запізнюється, `@import` не розгортається — обидва факти
  перевірені емпірично). Ціна: ще одна команда в `Як підняти локально`, легко забути. Пом'якшення
  — Фаза 1 може додати перевірку "чи generated-CSS новіший за дані граматики" у сам `cargo leptos
  build`-обгортку (якщо вона буде) або просто в `MEMORY.md`/pre-commit нагадування.
- Рецепти (варіанти компонентів) — ще один шар абстракції поверх headless-логіки, яка вже є
  (`components::Select` тощо) — Фаза 3 (міграція) покаже, чи виправдано для кожного компонента,
  чи для частини досить голого `cx!()`.

## `ui-visual-style-source.md` — статус

Палітра й шрифти лишаються ТІ САМІ (виміряно зі striy.pp.ua) — цей документ далі джерело істини
для КОЛЬОРІВ/ШРИФТІВ. Спосіб РЕАЛІЗАЦІЇ (як ці значення потрапляють у CSS) замінено новою
стильовою системою (`08-style-system.md`) — сам `ui-visual-style-source.md` не редагувався по
суті, лише отримав рядок-посилання на новий документ (див. коміт).
