# Брокер — NATS + JetStream, не Kafka/Redpanda/RabbitMQ/лише-Postgres

**Чому:** сервер має 8 ГБ разом з Postgres (~2-3 ГБ) і застосунком (~200-400 МБ) — бюджет під
брокер обмежений. Kafka (KRaft) і Redpanda розраховані на ≥1-2 ГБ/ядро й промисловий масштаб,
якого нема; RabbitMQ важчий і стріми (потрібні для персистентного `NOTIFY_CMD`/`NOTIFY_RESULT`
з повторами) — не рідна модель Erlang-брокера. "Лише Postgres" (SKIP LOCKED/pgmq) не дає
ізоляції сервісів — нотифікатору знадобився б прямий доступ до БД застосунку, що суперечить
"власна схема, не бачить таблиць застосунку" (09-messaging.md §3.7).

NATS + JetStream — один бінарник (~50-150 МБ, ліміт контейнера 256 МБ), персистентні стріми,
work-queue, повтори/backoff, DLQ, дедуплікація за заголовком (`Nats-Msg-Id`), права на subject-и,
офіційний зрілий `async-nats`-клієнт. Повна таблиця альтернатив — `docs/spec/09-messaging.md` §2.

**Замінює транспорт із `[[depersonalized-notification-outbox]]`**: та нотатка (2026-09-27)
описувала простішу архітектуру — одна таблиця `notification_outbox` напряму в БД застосунку,
доставка тим самим процесом через трейт `NotificationChannel`. `09-messaging.md` — новіша й
детальніша: транзакційний `outbox` (загальний, не лише сповіщення) → NATS JetStream → ОКРЕМИЙ
сервіс `notifier` зі своєю БД/схемою. **Доменні правила лишаються чинними** (знеособлений
шаблон, `org_contact`, антиспам N год, дзвіночок завжди незалежно від зовнішнього каналу,
04 §5) — просто виконуються тепер у `notifier`, не в тому самому процесі, що `app`. Стара
нотатка НЕ видалена — вона документує "чому взагалі окрема черга", лишається історією рішення;
цей запис документує "чому саме такий транспорт".

**Як застосовувати:** структура — `docs/spec/09-messaging.md` §3-4 (архітектура, теми/стріми,
конверт, безпека, структура воркспейсу). Перевірено вручну проти РЕАЛЬНОГО `nats-server -js`
(не мок) у Docker, Фаза 0 цього рішення: publish з `Nats-Msg-Id` + durable pull-consumer +
брокерна дедуплікація — усі три працюють саме так, як описано в §3.1 (`bus/tests/pubsub.rs`).

## Фаза 3 — автентифікація: user/password + права, не nkeys

**Рішення**: `authorization { users: [...] }` (`docker/nats-server.conf`) — один глобальний account
(не окремі `accounts { APP {} NOTIFIER {} }` з export/import: той варіант ізолює subject-простори
один від одного за замовчуванням, вимагаючи додаткової конфігурації, щоб notifier взагалі бачив
події app і навпаки — зайва складність для одного сервера). User/password, не nkeys — простіше
конфігурувати й дебажити на одному сервері, ціна (пароль у конфіг-файлі) прийнятна для
внутрішньої docker-мережі (`internal`, без шляху з інтернету).

**Перевірено проти РЕАЛЬНОГО nats-server** (окремий тимчасовий контейнер із цим конфігом, не
теоретично): `app` публікує `vyshkil.discrepancy.>` — дозволено; `notifier` намагається
опублікувати `vyshkil.discrepancy.>` (чужий, app-only subject) — `Permissions Violation`,
відхилено; `notifier` публікує `vyshkil.notify.result.v1` — дозволено; невірний пароль —
`Authorization Violation` при конекті. Перша версія тесту також перевіряла "app publish
notify.send.> має бути заборонено" — це МОЯ власна помилкова передумова: сама спека (§3.6) прямо
каже, що `app` МАЄ публікувати `vyshkil.notify.send.>` (майбутній outbox-продюсер "кого
сповіщати"), а `notifier` лише споживає — виправлено в конфізі, не в спеці.

**Реальна пастка, спіймана в цьому прогоні**: перша спроба показала "jetstream is not enabled"
на `notifier`-публікації, що виглядало як помилка прав — виявилось, що я просто не створив стрім
`NOTIFY_RESULT` у тестовому скрипті (ще один вияв "спершу перевір найпростіше пояснення" — не
кидайся одразу правити конфіг прав, якщо помилка може бути в тестовому сетапі).

**Свідомо не зроблено**: локальний ad hoc dev-NATS (ручний `docker run ... nats:2-alpine -js` без
конфігу, яким користувався весь цей сеанс для швидких перевірок) лишається БЕЗ автентифікації —
зручність для разових перевірок, не шлях розгортання. `docker-compose.yml` (реальний шлях
розгортання) — з автентифікацією, паролі поки як dev-значення в конфіг-файлі (`docker/
nats-server.conf`), не через секрети хоста — для продакшену замінити на справжній
secrets-механізм, не комітити реальні паролі.
