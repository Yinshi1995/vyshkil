# Dev-VM на Proxmox — параметри (Фаза 0, `docs/spec/10-dev-vm.md` §1)

Зафіксовані відповіді замовника + реальна інвентаризація хоста (`pveversion`, `pvesh`, `pvesm`,
`lsblk`, мережа) — джерело для `infra/ansible/`, не вгадано.

## Proxmox
- PVE 9.2.2, один вузол (`pidhotovka`), без кластера.
- Доступ — API-токен `ansible@pve!provision` (privsep 0), права: `PVEVMAdmin` на `/vms`,
  `PVEDatastoreUser` на `/storage/local-lvm`, `PVEDatastoreAdmin` на `/storage/local` (потрібен
  для імпорту cloud-образу через `download-url`), `PVESDNUser` на `/sdn/zones/localnetwork`,
  `PVEAuditor` на вузол. Секрет токена — лише в Ansible Vault, не в git, не в чаті.
- Storage: системний диск dev-VM → `local-lvm` (LVM-thin на NVMe, ~345 ГБ вільно на момент
  інвентаризації). `ncdata` (ZFS, дзеркало 2×8 ТБ HDD) — НЕ для компіляції (повільний, для Nextcloud
  і LXC-даних). Образи/шаблони → `local` (content `import,iso,vztmpl,backup`). PBS нема, `vzdump`
  не налаштовано — бекапів VM немає взагалі (не лише для ДСК-диска).
- Шаблону нема → створюється з нуля: Ubuntu 24.04 LTS cloud-image з `cloud-images.ubuntu.com`
  (досяжний з хоста, перевірено), VMID **9000**, конвертується в template.
- Dev-VM — **VMID 300**.

## Розмір VM — СКОРИГОВАНО під реальні ресурси хоста (не мінімуми з §3 специфікації)
Хост: AMD Ryzen 5 5600GT, 6 ядер/12 потоків, 14.9 ГБ RAM фізично, ~8 ГБ вільно понад уже запущені
LXC/VM (`striy-*`, `nextcloud-lan`, `pihole`, `lan-proxy`, `home-portal`, `vyos-router`). Апгрейд
RAM — **не підтверджено, не чекаю**: замовник прямо сказав забрати все вільне.

| Ресурс | Значення | Чому саме так |
|---|---|---|
| vCPU | 6 (тип `host`) | з 12 потоків хоста — лишає 6 для вже запущених сервісів і самого PVE |
| RAM (guest) | 8192 МБ | все вільне на хості на момент інвентаризації (`MemAvailable` ~8 ГБ); далі нічого на хості не апгрейдиться |
| Swap (guest) | 8 ГБ | страховка від OOM при лінковці/LTO — САМЕ swap, не робоча памʼять; без нього `cargo leptos build --release` реально впаде |
| Диск системний | 150 ГБ, thin, `discard=on`, `ssd=1`, на `local-lvm` | `target/` (debug+release+wasm), `~/.cargo/registry`, docker-образи, sccache |
| Диск ДСК | **не створюється** | див. нижче — `source_files/` на VM поки нема |
| `CARGO_BUILD_JOBS` | 4 | явне обмеження паралелізму компіляції під 8 ГБ RAM — без цього паралельна лінковка кількох crate-ів одночасно зʼїдає все й OOM-killer вбиває збірку |
| Лінкер | mold (запасний варіант — lld, якщо mold не збереться/не буде в репо) | швидший і економніший по RAM за `ld.bfd`; обрати й заміряти в Фазі 3 |

**Явний компроміс, записаний відкрито:** release-збірка з LTO + повний `docker compose up` (db+nats+app+notifier з Chromium, `mem_limit: 1g`+`shm 512m`) + Playwright одночасно на 8 ГБ —
НЕ гарантовано вміститься. Фаза 4 (§5 специфікації) мусить замірити реальний пік RSS і, якщо
впирається, Фаза 4 виконується послідовно (build release → зупинити → підняти docker-стек), а
не паралельно — задокументувати в `infra/README.md` як реальне обмеження, не мовчки вважати
вирішеним.

**Для `docs/spec/11-prod-deploy.md`:** прод на цьому самому фізичному хості без апгрейду RAM
НЕ поміститься (прод-стек + ця ж dev-VM одночасно впевнено перевищують 14.9 ГБ) — позначка
внесена в сам документ 11.

## Мережа — DHCP НЕ ПРАЦЮЄ, перейдено на статику (знайдено емпірично, Фаза 2)

Перша спроба з `ipconfig0=ip=dhcp` стабільно зависала: VM стартує, ~100-110с інтенсивного
дискового запису (ext4-метадані при форматуванні/resize — масштабується з розміром диска,
перевірено на 4 ГБ і 150 ГБ дисках однаково), потім повна тиша — ні `qemu-guest-agent`, ні SSH,
ні хоста в ARP/скані LAN, незалежно від розміру диска (виключає resize2fs як причину) і від
навантаження хоста (перевірено — вільно 9/16 ГБ RAM, swap не займано, loadavg 0.05). Висновок:
домашній роутер не видає оренду DHCP для нового MAC цієї VM (ймовірно, MAC-фільтрація/вайтліст —
узгоджується з тим, що решта мережі замовника вже сегментована й контрольована).
**Фікс**: статична IP (`192.168.1.200/24`, шлюз/DNS `192.168.1.1`) — SSH піднімається за ~14с
замість "ніколи". Записано як постійне рішення, не обхідний костиль: `dev_vm_ip_cidr`/
`dev_vm_gateway` в `group_vars/all.yml`.

**Побічна знахідка, НЕ пов'язана з DHCP**: `qemu-guest-agent` не є частиною цього конкретного
Ubuntu 24.04 cloud-image (`systemctl status` → "Unit ... could not be found") — не помилка, роль
`base` вже встановлює пакет у Фазі 3, нічого змінювати не треба.

## Мережа — СПРОЩЕНО відносно §1.6-9 специфікації
Замовник прямо відмовився від окремого VLAN/підмережі через VyOS для dev-VM: **`vmbr0`** (та сама
домашня LAN `192.168.1.0/24`, де вже сидить і сам Windows-хост розробки), **DHCP** — та сама
схема адресації, що й у Windows-машини, без VLAN-тегу, без маршрутизації через VyOS.

**Наслідок, записаний відкрито:** dev-VM в тій самій довірчій зоні, що й Windows-хост і домашня
LAN — НЕ за VyOS-сегментацією, на відміну від усіх інших сервісів хоста (`data-vlan`/`admin-vlan`/
`infra-vlan`/`web-vlan`/`edge-vlan`, усі — на `vmbr10` під маршрутизацією/файрволом VyOS). Це
свідоме спрощення для dev, не шаблон для проду: `docs/spec/11-prod-deploy.md` зберігає власну,
сувориішу вимогу до мережі (VyOS-сегментація, `DOCKER-USER`-файрвол, egress-проксі з allowlist) —
прод-мережу переносити з dev НЕ можна.
Файрвол dev-VM обмежується власним nftables на гості (вхідні — тільки SSH), VyOS-правил для
dev-vlan не існує, бо dev-vlan не створюється.

## Підключення й доступ до застосунку
VPN на VyOS → SSH на dev-VM; веб-застосунок (3000) і NATS-монітор (8222) — тільки через
SSH-тунель (`ssh -L 3000:localhost:3000 dev-vm`), не публікуються на інтерфейс.

## Код
Git-remote: **bare-репозиторій прямо на dev-VM** (`/srv/git/vyshkil.git` або аналог) — простіший
старт, без окремого сервісу (Gitea відкладено, не було явного підтвердження і це зайва залежність
для одного розробника). Windows стає `git remote add vm ssh://dev@<ip>/srv/git/vyshkil.git`.
Можна мігрувати на Gitea (`ncdata`) пізніше без зміни цього рішення — bare-репо просто перестане
бути єдиним remote.

**Відкрито, знайдено у Фазі 5 (2026-10-01), ще НЕ вирішено**: цей bare-репо досі порожній —
перший `git push vm main` із Windows ще не виконаний (попередня спроба замовника впала
`Permission denied (publickey)`, ймовірно особистий ключ без агента в той момент, не збій
сервера). Робоча копія `~/vyshkil` на VM зараз існує, але НЕ як клон bare-репо — вона була
занесена прямим rsync усього робочого дерева (разом із `.git`), тому досі вказує `origin` на
GitHub і має зайвий самопосилальний `vm`-remote, скопійований з Windows. Окремо: сам хост VM
(не лише docker-мережі) НЕ резолвить зовнішні домени через LAN DNS (192.168.1.1, search-домен
`inner.mod.ua`) — `ping 8.8.8.8` і `curl --resolve github.com:443:<ip>` працюють, голий
`curl https://github.com` падає на резолвінгу. Це виглядає на мережеву політику замовника
(військова мережа), не на хибу VM — свідомо НЕ обходжу мовчки (публічний DNS/hosts-запис),
рішення за замовником (деталі й конкретні команди для відновлення — `.claude/memory/MEMORY.md`,
Фаза 5).

## `source_files/` (ДСК) на dev-VM
**Не копіюється** — явного "так" не було (було лише мовчання після прямого питання), а правило
специфікації (10 §1.11) каже: без явного "так" не копіювати. Тести, що потребують `source_files/`,
лишаються skip на dev-VM так само, як зараз на Windows. Якщо замовник пізніше скаже "так" —
додається окремий віртуальний диск `backup=0` на `local-lvm`, без зміни решти плану.

## Claude Code і control node
- Автентифікація Claude Code на VM — підписка, `/login` виконує замовник сам по SSH після Фази 3.
- Control node — WSL2, дистрибутив **Arch Linux** (не Ubuntu 24.04, як рекомендувалось у §1.13) —
  вже існував на машині замовника (`wsl -l -v` показав `archlinux`, запущений лише `docker-desktop`).
  Функціонально байдуже для Ansible (дистро-агностичний), тому дистрибутив control node НЕ
  переставлявся заради відповідності рекомендації. Встановлено й перевірено: `ansible-core 2.21.4`,
  `ansible-lint 26.9.0`, колекція `community.proxmox 2.0.0` (актуальна назва — модулі справді
  переїхали з `community.general`, перевірено на момент встановлення, не з пам'яті).
  **Грабля, знайдена тут:** `pacman -Sy` (без `-u`) синхронізує базу, але лишає систему в
  частковому апдейті (partial upgrade) — зловлено по факту: щойно встановлений `python3.14`
  вимагав `GLIBC_2.44`, якого не було в системному `glibc`, бо він не оновився разом. Виправлено
  повним `pacman -Syu`. Висновок для будь-якого майбутнього `pacman`-кроку в цьому control node:
  **ніколи `-Sy` без `-Syu`**, тільки повний апгрейд.
