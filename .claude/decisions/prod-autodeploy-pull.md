# Автодеплой проду з GitHub — таймер на прод-VM, що сам збирає образи

## Контекст

Замовник хоче "як у Railway": пуш у `main` → прод оновлюється сам. Прод-VM (2 ГБ RAM) за VyOS,
вхідних з інтернету нема. Репозиторій публічний.

- Ревізія 1 (таймер на dev-VM) скасована: dev-VM тимчасова, деплой не може залежати від машини
  розробника.
- Ревізія 2 (GitHub Actions → GHCR) скасована: акаунт GitHub заблоковано за billing, Actions не
  стартують; замовник платити GitHub відмовився. Від GitHub лишається тільки git-хостинг.

## Рішення

systemd-таймер на самій прод-VM (`roles/prod_autodeploy`, `infra/deploy/deploy-prod.sh`) щохвилини
робить `git fetch` публічного репо; новий коміт `main` → збірка образів ТУТ → бекап БД →
`:latest` (старі → `:previous`) → `compose up` → перевірка → відкат при збої.

Збірка Rust з LTO не влазить у 2 ГБ, тому:
- окремий buildx-builder (`docker-container` driver) з лімітом пам'яті/CPU — робочий стек
  (Postgres/app/notifier) не потрапляє під OOM і не голодує за CPU;
- додатковий swap `/swap-build` (6 ГБ, нижчий пріоритет);
- кеш-маунт `target/` у Dockerfile — повторні збірки інкрементальні.

## Наслідки

- Деплой повільніший, ніж на потужній машині (перша збірка — довго, далі — інкрементально).
- Жодної залежності від GitHub, крім `git fetch`; жодних ключів/токенів поза продом.
- Коли dev-VM вимкнуть, звільнену RAM хоста варто віддати прод-VM — збірка пришвидшиться.
- Деплоїться лише код. compose/env/NATS-конфіг — `playbooks/prod-vm.yml`.
- Міграції незворотні; бекап перед кожним деплоєм у `/opt/vyshkil/backups` (останні 14).
