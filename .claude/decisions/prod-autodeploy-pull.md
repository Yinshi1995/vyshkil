# Автодеплой проду з GitHub — GitHub Actions → GHCR → таймер на прод-VM

## Контекст

Замовник хоче "як у Railway": пуш у `main` → прод оновлюється сам. Прод-VM (2 ГБ RAM) за VyOS,
вхідних з інтернету нема; Rust там не зібрати. Репозиторій публічний.

Ревізія 1 (таймер на dev-VM, що збирає й заливає образи) **скасована**: dev-VM тимчасова,
замовник перейде на ноут — ланцюжок деплою не може залежати від машини розробника.

## Рішення

- **Збірка** — GitHub Actions (`.github/workflows/images.yml`, hosted runner): образи
  `ghcr.io/yinshi1995/vyshkil-{app,notifier}:<sha>`, потім обидва атомарно отримують `:main`.
- **Доставка** — pull: системний таймер на самій прод-VM (`roles/prod_autodeploy`,
  `infra/deploy/deploy-prod.sh`) щохвилини тягне `:main`; новий revision → бекап БД → образи
  `<sha>` → `:latest` (старі → `:previous`) → `compose up` → перевірка → відкат при збої.

## Чому так

- GitHub нічого не знає про інфраструктуру: жодних SSH-ключів, self-hosted runner-ів чи вхідних
  з'єднань. Self-hosted runner на публічному репо = виконання коду з чужих PR поряд із продом.
- Прод потребує лише вихід на ghcr.io (VyOS rule 900 SRV→internet вже дозволяє).
- Образи публічні в GHCR — як і сам репозиторій; ДСК-даних у них нема (`source_files/` у
  `.dockerignore`, у git їх теж нема).

## Наслідки

- Пакети GHCR після першого пуску workflow треба один раз зробити Public (за замовчуванням
  private) — інакше прод не стягне без токена.
- Деплоїться лише код (образи). compose/env/NATS-конфіг — як і раніше `playbooks/prod-vm.yml`.
- Міграції незворотні: відкат образу не відкочує схему; бекап перед кожним деплоєм у
  `/opt/vyshkil/backups` (останні 14).
