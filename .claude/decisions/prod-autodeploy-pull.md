# Автодеплой проду з GitHub — pull-таймер на dev-VM

## Контекст

Замовник хоче, щоб пуш у `main` на GitHub автоматично потрапляв на прод "як у Railway".
Прод-VM (2 ГБ RAM) за VyOS, вхідних з інтернету нема; Rust там не збирається. Репозиторій
публічний.

## Рішення

systemd user-таймер на dev-VM (`roles/prod_autodeploy`, скрипт `infra/deploy/deploy-prod.sh`)
щохвилини робить `git fetch` дзеркала; новий коміт `main` → збірка образів на dev-VM → бекап БД
проду → `docker save | ssh docker load` → `compose up -d` → перевірка (HTTP 200, без panic) →
при збої відкат на тег `:previous`, коміт позначається невдалим і не ретраїться до наступного.

## Чому не GitHub Actions

- Self-hosted runner на ПУБЛІЧНОМУ репо = виконання чужого коду з PR на машині з доступом до
  проду (рекомендація GitHub — не робити).
- Hosted runner + GHCR: прод мав би тягнути образи з інтернету з токеном, а GitHub — знати про
  інфраструктуру; і збірка без кешу (~повільніше), ніж на dev-VM.
- Pull-модель: жодних вхідних з'єднань, токенів чи секретів у GitHub; затримка ≤1 хв + збірка.

## Наслідки

- dev-VM тримає ключ `deploy@прод` (`~/.ssh/vyshkil-prod`) — компрометація dev-VM = доступ до
  проду. Прийнятно для поточного масштабу; звузити — окремий ключ з `command=`-обмеженням.
- Деплоїться лише образ app/notifier. Зміни compose/env/nats-конфігу — як і раніше Ansible
  (`playbooks/prod-vm.yml`).
- Міграції незворотні: при відкаті образу БД лишається мігрованою; бекап перед кожним деплоєм
  у `/opt/vyshkil/backups` (останні 14).
