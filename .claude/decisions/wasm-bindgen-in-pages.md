# wasm-bindgen/web-sys як прямі залежності `app` (не лише транзитивні через leptos)

## Контекст

Сітка введення (Етап 4, `pages/training_form`) вимагає керування з клавіатури: після Tab/Enter/
стрілки фокус мусить програмно переміститись у наступну клітинку (`document().get_element_by_id(id)`
→ `.dyn_into::<web_sys::HtmlElement>()` → `.focus()`), а обробники `on:keydown` типізовані як
`web_sys::KeyboardEvent`, щоб читати `ev.ctrl_key()`/`ev.shift_key()`/`ev.key()`.

`leptos` уже тягне `wasm-bindgen` і `web-sys` транзитивно (інакше сам фреймворк не зібрався б для
wasm), але щоб НАЗВАТИ ці типи в коді (`web_sys::HtmlElement`, `wasm_bindgen::JsCast`), крейти
мають бути в `[dependencies]` `app/Cargo.toml` явно — Rust не дозволяє використовувати типи чужого
транзитивного крейта без прямого оголошення залежності.

## Рішення

Додано `wasm-bindgen = "0.2"` (та сама версія, що вже закріплена в `frontend/Cargo.toml`) і
`web-sys = { version = "0.3", features = ["HtmlElement", "KeyboardEvent"] }` як **звичайні**
(не `optional`, не під feature `hydrate`) залежності `app`.

Свідомо НЕ під feature `hydrate`: Leptos рендерить те саме дерево `view!` і на сервері (SSR —
розмітка без реального DOM), і на клієнті (гідрація) — той самий вихідний файл компілюється під
обидва набори фіч. Типи `web_sys`/`wasm_bindgen` — структурні визначення (біндинги wasm-bindgen),
компілюються на будь-якому таргеті; лише їхні МЕТОДИ (виклик `.focus()` тощо) реально щось роблять
у браузері. Функції-обробники подій (`on:keydown`, `Effect::new`) фізично викликаються лише
клієнтом (Leptos не запускає їх під час SSR), тож немає ризику паніки на сервері — просто код,
що ніколи не виконується там, де DOM немає.

Це ІНША ситуація за `chrono` ([[chrono-in-domain]]): там ішлося про `domain/` — шар, що навмисно
не залежить від `leptos` взагалі і мусить лишатись мінімальним. Тут — навпаки, `pages/` — саме
місце, де реальний UI-код і DOM-типи є нормою, а не винятком.

## Альтернативи, які відкинуто

- **`NodeRef` замість `id` + `get_element_by_id`**: ідіоматичніше для статичних елементів, але
  сітка прогресивно дорендерюється (рядки монтуються по мірі скролу, ніколи не демонтуються) —
  зберігати `NodeRef` окремо для кожної клітинки різних типів (`Input`/`Select`) в одній мапі
  ускладнило б код без реальної переваги. `id`-based фокус — простіший, однаково коректний за
  такого способу рендеру.
