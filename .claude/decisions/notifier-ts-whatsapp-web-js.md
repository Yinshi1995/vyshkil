# Нотифікатор — TypeScript + whatsapp-web.js, рантайм Node 22 LTS (не Bun)

**Чому TS, не Rust** (заміняє попереднє формулювання 09-messaging.md §3.7, яке
припускало Rust-бінарник): зріла екосистема WhatsApp-клієнтів у npm — жодної повноцінної,
підтримуваної Rust-бібліотеки з рівнем зрілості `whatsapp-web.js` нема. Вибір бібліотеки — рішення
замовника (`whatsapp-web.js`, не `@whiskeysockets/baileys` — одна бібліотека, не дві).

**Ціна**: Chromium у контейнері нотифікатора (~300-500 МБ RAM у спокої, більше під час активної
сесії) — прийнятно в межах бюджету 8 ГБ (NATS ≤256 МБ, застосунок ~200-400 МБ, Postgres ~2-3 ГБ,
даного контейнера має вистачити запасу).

**Ризики**: неофіційний клієнт (реверс-інжиніринг WhatsApp Web, не офіційне API) — можливе
блокування номера при надто активній розсилці чи зміні WhatsApp свого протоколу. Мітигація:
окремий службовий номер (не робочий/особистий), технічний rate-limit + випадкова пауза між
надсиланнями (§3), готовність перелінкувати сесію без втрати черги (durable consumer + inbox).

## Bun vs Node — перевірено емпірично, не на слово

**Метод**: мінімальний скрипт (`Client` + `LocalAuth`, `puppeteer.executablePath` на локальний
Chrome, чекаємо подію `qr`) запущено ОБОМА рантаймами — `bun run index.ts` і `node
--experimental-strip-types index.ts` — з ідентичним кодом, послідовно, на тій самій машині.

**Результат**: ОБИДВА рантайми впали на ТІЙ САМІЙ точці з ІДЕНТИЧНОЮ помилкою —
`ProtocolError`/`Error: Execution context was destroyed, most likely because of a navigation` у
`Client.inject()` (`whatsapp-web.js/src/Client.js:126`, крок ін'єкції бутстрап-скрипта в
завантажену сторінку WhatsApp Web). Помилка відтворилась і при повторному запуску під Bun (не
флейк). **Bun і Node дали однаковий результат — це НЕ Bun-специфічна проблема.**

**Ймовірна причина** (не остаточно підтверджена, але добре узгоджується з фактами): локальний
Chrome на цій машині — версія 154.0.8037.58 (дуже свіжа), тоді як `whatsapp-web.js@1.34.7`
залежить від `puppeteer@24.38.0`, який тестувався/постачається з конкретною відповідною
`chrome-headless-shell` (~131 на момент випуску puppeteer 24.x) — версійний перекіс між системним
Chrome і тим, що puppeteer/wwebjs очікують, добре відомий клас проблем для цієї бібліотеки
(підтверджено пошуком — profile схожих issues на GitHub `pedroslopez/whatsapp-web.js`). Пряме
підтвердження (запуск з puppeteer-власним завантаженим Chromium) НЕ вдалось перевірити тут:
`storage.googleapis.com` не резолвиться з цієї машини (DNS timeout — мережевий артефакт ЦІЄЇ
машини/мережі, не сандбокса й не майбутнього контейнера — `web.whatsapp.com` резолвиться й
відповідає 200 нормально).

**Рішення**: рантайм — **Node 22 LTS**, не Bun. Не тому що Bun довів свою непридатність (тест
цього не показав — обидва впали однаково), а тому що: (1) немає жодної переваги Bun у цьому
конкретному сценарії, яка компенсувала б менш протестовану сумісність з Puppeteer/`proxy-agent`
(відомий клас проблем — знайдено в пошуку незалежно від цього тесту); (2) `whatsapp-web.js`
екосистема (issues, приклади, підтримка спільноти) — уся на Node; (3) `engines.node` самого
пакета вимагає `>=18.0.0`, Bun там не згаданий і не тестується проєктом `whatsapp-web.js`.

**Оновлення після повного прогону сервісу** (не лише ізольованого мінімального скрипта):
запустивши весь `services/notifier` (§3 нижче) — міграції, NATS, `PairingStateMachine`,
`Client.initialize()` — QR РЕАЛЬНО згенерувався й опублікувався в NATS KV bucket
`notifier_status` (перевірено прочитанням запису напряму: `{"state":"pairing","qr":"2@...",
...}`). "Execution context was destroyed" із ранішого ізольованого тесту відтворилась лише
частково (2 з 3 прогонів) — це схоже на флейк "холодного старту" Chromium (перший запуск
повільніший, можливий race між навігацією й ін'єкцією), не гарантований версійний блокер.

**У реальному Docker-контейнері** (не лише на хості) — системний `chromium` спершу НЕ стартував
узагалі: `No usable sandbox! ... please install the chromium-sandbox package`. `--no-sandbox` НЕ
застосовано (§3 явно забороняє мовчки); замість цього — `cap_add: SYS_ADMIN` у
`docker-compose.yml`'s `notifier`-сервісі (вужче за `--privileged`, саме та можливість, яку
Chromium's user-namespace sandbox потребує): з цим прапорцем контейнер стартує Chromium БЕЗ
`--no-sandbox` і доходить до реального QR (перевірено — той самий KV-запис, що вище, зсередини
контейнера через `host.docker.internal`). `WA_DISABLE_SANDBOX=true` (код підтримує, голосно
попереджає в логах) лишається аварійним перемикачем на випадок, якщо `SYS_ADMIN` виявиться
недостатнім на конкретному хості розгортання (інше ядро/AppArmor-профіль) — не дефолтна поведінка.

Досі не проведено: реальне сканування QR телефоном (§6, довести до `connected`) — потребує
фізичного службового номера користувача, окремий крок.
