# Інфраструктура — Ansible, не разовий скрипт

**Чому:** прод-деплой (`docs/spec/11-prod-deploy.md`, відкладено, але вже ТЗ) однаково буде на
Ansible — ролі `base`, `docker`, `firewall`, які пише dev-VM (`docs/spec/10-dev-vm.md`), прод
перевикористовує без переписування. Одна VM — не аргумент проти Ansible: плейбук невеликий, а
"скрипт, який вже налаштовував машину" не можна безпечно перезапустити після ручних змін на
VM — ідемпотентність (повторний прогін = `changed=0`) потрібна вже на dev-VM, не тільки в проді.

**Створення самої VM** (`provision-dev-vm.yml`) — через колекцію `community.proxmox` (API-токен,
§1.2 відповіді замовника), не через SSH-скрипт на хості PVE-хості: доступ є саме токеном, SSH на
сам гіпервізор замовник не відкривав і не планував (навмисно тримає гіпервізор чистим).

**Перевір актуальну назву колекції** (виконано): модулі Proxmox дійсно переїхали з
`community.general` в окрему колекцію — на момент цього рішення чинна назва `community.proxmox`,
встановлена версія `2.0.0` (`ansible-galaxy collection install community.proxmox`,
control node — WSL2/Arch, див. `[[dev-vm-parameters]]`). Версія зафіксована в
`infra/ansible/requirements.yml`, не "latest" без фіксації.

**Control node:** WSL2 на Windows-машині розробника (той самий потім піде на прод, `11 §1`) —
Ansible не працює нативно на Windows. Дистрибутив — вже наявний Arch Linux WSL, не встановлювався
окремо Ubuntu 24.04 (рекомендація з `10 §1.13`), бо дистрибутив control node функціонально не
впливає на роботу Ansible проти Linux-хостів.
