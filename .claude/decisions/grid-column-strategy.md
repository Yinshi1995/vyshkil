# Grid — стратегія колонок/sticky/drawer (розділ Б)

**Контекст**: `docs/spec/components/grid.md` — повна анатомія. Тут — лише рішення й "чому",
коротко, для швидкого пошуку.

**Drawer, не модалка (підтверджено, не змінено).** 02-input-forms-ux.md §1 — уся сторінка про
"швидше ніж в Excel", ніколи не відпускати клавіатуру; модалка ховає сітку повністю, не можна
звірити сусідній рядок. `components::Drawer` вже саме для цього (`row_editor.rs`) — розділ Б
добудовує навколо (Ctrl+E, індикатор помилки/заповненості в колонці дій, повернення фокуса при
закритті), не змінює парадигму.

**Секундарні поля йдуть ЛИШЕ в drawer** (розподіл/організатор/підстава/примітка) — 11 живих
треків замість 15. `RowEditor` уже повний (перевірено розвідкою) — переробки вмісту НЕ потрібно.

**Ширини колонок — фіксована таблиця з `min_px`/`default_px` за типом** (дія 40, частина
160/200, вид 130/160, ВОС/посада 180/220, ОВТ 130/160, місце 160/200, дата 90/110, число 64/80)
— точні числа й обґрунтування в `docs/spec/components/grid.md` §1. Resize — перетягування,
не звужує нижче `min_px`. Персистентність — `localStorage`, per-viewer, без серверної сторони
(немає потреби ділитись між пристроями чи людьми).

**`Combobox` отримує третій вимір `ComboboxMode::Input`** ("інпут сам тригер") замість нового
окремого компонента — Mantine-принцип "один двигун" з розділу А застосовується послідовно.
`OrgAutocomplete`/`VosPositionCourseAutocomplete` лишаються як публічний контракт
(`widgets/group_grid/autocomplete.rs`), але всередині тепер тонкі обгортки над `Combobox`.

**Дати "З"/"По" — окремий домен-обізнаний `widgets/group_grid/date_range_cell.rs`**, НЕ
розширення `components::DatePicker`. Причина: гнучкий розбір ("18.08" без року, діапазон в
одне поле, висновок року) — це `domain::dates`, а `components/` архітектурно не знає домену.
`DatePicker` лишається незмінним для "Станом на" (суворий формат там доречний і вже працює).

## Реальний баг, знайдений під час перевірки наживо (не в первинній збірці)

`domain::dates::parse_date`'s правило "явний рік у тексті = рік `as_of`" (проти друкарських
помилок при наборі) виявилось несумісним із тим, що САМ `date_range_cell` іноді пише назад
ПОВНІСТЮ розв'язану дату з явним роком (вибір у календарі, авторозклад діапазону "18.08-09.10")
— той рік ЗАКОНОМІРНО може не збігатись із `as_of.year()` (перехід через Новий рік, ще не
заповнене "Станом на"). Повторна валідація тим самим строгим правилом фальшиво позначала щойно
правильно вирішену дату як помилку. Виправлено двома змінами:
1. Авторозклад більше НЕ переписує поле "З" повністю розв'язаною датою — лишає як набрано
   (рік-less, якщо рік-less і набрано), пише розв'язану дату лише в "По" (`split_range` — тепер
   `pub` у `domain::dates`, з поясненням чому в доккоменті).
2. Для ВІЗУАЛЬНОЇ валідності полів (не для збереження) — нова лінива перевірка `lenient_parse`
   (`date_range_cell.rs`, `pub(super)`, переюзана і в `grid.rs`'s індикатора помилки рядка):
   перевіряє лише "чи реальна дата" (день/місяць існують для вказаного року), БЕЗ звірки з
   `as_of` — те правило залишається чинним ЛИШЕ для `parse_date`/`parse_maybe_range`'s власного,
   первинного призначення (нове ручне введення користувачем), не для повторної перевірки вже
   розв'язаного власного виводу. `domain::dates::split_token` — теж тепер `pub`, той самий привід.

Знайдено методом розділу А: живе вимірювання через Playwright (`localStorage`/DOM-класи
`cell__input--invalid`), не візуальний огляд — фальшива помилка на валідному діапазоні
("18.08.2025"–"09.10.2025") не була б помітна без прямого читання класів клітинок.
