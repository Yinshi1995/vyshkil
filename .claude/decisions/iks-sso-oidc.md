# Вхід через ІКС (OIDC, Pocket ID) — єдиний штатний спосіб входу

## Контекст

У частині працює власний OIDC-провайдер Pocket ID ("ІКС", `https://id.lab.okpivden.uk`,
вхід passkey-ключем). У кожної людини один профіль ІКС, і користувач хоче, щоб ім'я, звання,
позивний, телефон, нік Delta й аватар були спільними для всіх застосунків. Раніше
([[auth-architecture]], варіант C) OIDC відкидали через "жодних мережевих викликів назовні" —
але ІКС це внутрішня інфраструктура частини, а не зовнішній сервіс, тож правило не порушується.

## Рішення

1. **Authorization Code + PKCE (S256) + state + nonce**, конфіденційний клієнт
   (`client_secret_basic`), discovery `/.well-known/openid-configuration` (кеш 1 год).
   Скоупи `openid profile email groups`.
2. **id_token**: перевіряємо `iss`, `aud` (+`azp` при кількох aud), `exp` (допуск 60 с), `nonce`.
   Підпис не перевіряємо — токен отримано напряму з token endpoint по TLS з автентифікацією
   клієнта (OIDC Core §3.1.3.7 п.6); JWT-бібліотеки в репозиторії немає, заводити її заради
   цього не варто.
3. **Доступ** — лише якщо `groups` містить `OIDC_GROUP` (`vyshkil`).
4. **Мапінг**: `preferred_username` ↔ `user_account.login` без урахування регістру. При першому
   вході зберігаємо `sub` у `user_account.oidc_sub` (міграція 070). Логін, уже прив'язаний до
   іншого `sub`, або `sub`, прив'язаний до іншого логіна, — конфлікт, вирішує адміністратор
   (захист від перейменування/перестворення профілю в ІКС).
5. **Новий користувач**: створюється НЕАКТИВНИМ, роль `viewer` в організації першого
   адміністратора (той самий дефолт, що адмінське створення — org адміна), без пароля
   (хеш-заглушка `!sso`). Людина бачить «Обліковий запис створено, чекає адміністратора»;
   адмін активує в «Налаштування → Користувачі» / «Довідник». Чому не активним одразу: роль
   в org верхнього рівня дає перегляд усього дерева підпорядкування — це рішення людини, а не
   автомата; членство в групі ІКС лише пускає до черги.
6. **Профіль** (display_name, ім'я, прізвище, звання, позивний, телефон, нік Delta) —
   перезаписується з claims при кожному вході; аватар (`picture`) завантажується сервером лише
   з хоста ІКС у ту саму `data/avatars/`, що й ручне завантаження. Email у моделі немає — не
   зберігаємо. У налаштуваннях для таких акаунтів поля лише для читання, підказка «Профіль
   ведеться в ІКС».
7. **Сесія** — та сама cookie `session`, що й при вході за паролем; решта застосунку без змін.
8. **Пароль — лише аварійно**: вхід за паролем, зміна/скидання пароля, створення акаунта з
   тимчасовим паролем і «Запросити обліковий запис» працюють тільки при `PASSWORD_LOGIN=1`
   (за замовчуванням вимкнено: ендпоінти віддають 404, UI їх ховає).

## Ціна / ризики

- Стан незавершених входів у пам'яті процесу (TTL 10 хв) — після рестарту людина натискає
  кнопку ще раз. Для кількох реплік знадобиться спільне сховище.
- Без `PASSWORD_LOGIN=1` немає входу, якщо ІКС лежить. Аварійний шлях — увімкнути змінну.
- Існуючий `admin` увійде через ІКС, лише якщо в ІКС є користувач з логіном `admin` (або
  адміністраторові в базі перейменовано логін на його логін в ІКС).
