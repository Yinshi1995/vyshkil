# Структура `app/src`: спільне в корені, специфічне поруч, карти + тест

До цього рішення весь код застосунку жив у трьох плоских файлах (`app.rs`, `queries.rs`,
`normalize.rs`) — прийнятно для Stage 1 з двома сторінками, але вже стало плутаним:
`app.rs` змішував shell/роутинг/сторінки/компоненти/server-функції в одному 550-рядковому файлі,
і жодна `#[server]`-функція не перевіряла права, бо `server::policy` фізично недосяжний із
крейту `app` (Leptos вимагає, щоб `#[server]`-функції жили в `app`, а `server` залежить від
`app`, не навпаки).

## Рішення

`docs/spec/07-code-structure.md`: два принципи — (1) перевикористовуване в спільних теках
кореня (`components/`, `widgets/`, `services/`, `types/`, `domain/`, `backend/`), (2) специфічне
для однієї сторінки лежить поруч із нею (`pages/<p>/server.rs`, `pages/<p>/components/`).
"Правило двох" (§2.1): новий код починається поруч зі споживачем, переноситься нагору лише коли
з'являється другий реальний споживач — не наперед "про всяк випадок".

`policy` переїхав у `app/src/backend/policy.rs` (був недосяжний для `#[server]`-функцій у
`server/src/policy.rs`) — і одразу підключений: `search_orgs`/`get_subordination_tree`/
`get_org_detail` тепер приймають `actor: Option<Actor>` і фільтрують результат через
`policy::visible_org_ids`/`can_view_org` — перша реальна перевірка прав у проєкті.

## Чому карти (`CLAUDE.md`) і тест, а не просто структура

Плоска структура дешева для агента (`grep`/`ls` в одному місці), деревоподібна — ні: щоб
зрозуміти, куди класти новий код, довелось би або тримати всю структуру в контексті, або
рекурсивно сканувати теки щоразу. Карта `CLAUDE.md` у кожній непорожній теці (⩽40 рядків,
"можна/не можна" + таблиця "хто що використовує") дає ту саму дешевизну, що й плоский `ls`,
але для дерева — Claude Code вантажить її автоматично, щойно читає файл у цій теці.

Карта, яку ніхто не змушений оновлювати, брехатиме за тиждень. Тому `app/tests/architecture.rs`
(звичайний `cargo test`, без БД) перевіряє: кожна тека з ≥2 елементами має карту; кожен файл
теки згаданий у її карті; кожен шлях у карті реально існує; напрямок залежностей не порушено
(`components/` не знає домену, `domain`/`types` не тягнуть `leptos`/`sea_orm`); жодна сторінка
не імпортує іншу напряму; кожна `#[server]` лежить у дозволеному місці. Ціна — один файл тесту
й дисципліна оновлювати карту в тому ж diff (це ж перевіряє `spec-reviewer` перед комітом);
вигода — карта ніколи не розходиться з кодом мовчки, розбіжність ловить `cargo test`, а не
наступний агент, який повірив брехливій карті.

## Альтернативи, які відхилив

- **Залишити плоску структуру** — дешевше зараз, дорожче з кожним етапом (Stage 2+ додає
  довідники, словник фахів, форми — той самий `app.rs` став би нечитним).
- **CSS-колокація за тим самим принципом** (стилі компонента поруч із `.rs`) — досліджено
  окремо й відкладено: [[css-colocation-deferred]] (cargo-leptos не розгортає `@import`, і крок
  обробки стилів виконується до збірки Rust-крейта, тож `build.rs`-конкатенація теж не встигає).
