# Етап 8, зріз 1 — зіставлення подань + горизонтальна звірка (звуження обсягу)

**Контекст**: `docs/spec/04-reconciliation-notifications.md` — повна спека Етапу 8 (зіставлення,
3 типи звірки, розбіжності, внутрішні+WhatsApp сповіщення). За принципом "кожен етап —
вертикальний зріз" (`06-roadmap.md`, той самий, що дав D1-тоді-D2 в Етапі 7) беремо ПЕРШИЙ зріз.

## Що беремо зараз

- `reported_group` — постійний знімок "що подала ця сесія" (§2 спеки, буквально).
- Зіставлення при фіксації: ключ відправник+вид+(ВОС|курс|БЗВП)+місце+початок ±3 дні, запит по
  `training_group` напряму.
- Горизонтальна звірка (найпростіша з трьох — та сама канонічна група, різні подання) +
  автозакриття, коли нове подання усуває розбіжність.
- Екран `/discrepancies` — перегляд, фільтр орган/статус, значення поруч. Read-only (без
  workflow "взяти в роботу"/"закрити вручну" — лише перегляд + автоматичне відкриття/закриття).

## Що свідомо відкладено (не забуто, наступні зрізи)

1. **Неоднозначне зіставлення (2+ кандидати)** — спека хоче "питання користувачу в превʼю".
   Зараз: той самий шлях, що "0 кандидатів" (нова група) — не гірше за сьогоднішню поведінку
   (зараз ЗАВЖДИ нова група), не втрачає дані, не блокує коміт. UI-крок дизамбігуації — окремий
   зріз (це нова взаємодія в сітці/превʼю, не тривіальне дописування).
2. **`canonical_from` / яке значення "правда" при конфлікті** (§3 спеки: manual > table >
   повніше > свіжіше > pinned) — НЕ чіпаю `domain::counting`/запис `group_event`: конфліктні
   числа й далі пишуться як окремі події, так само, як сьогодні. Зробити це правильно вимагає
   або редизайну `domain::counting` (уже написаний, протестований, наскрізно використовується
   в Etapi 7 D1/D2), або механізму "яка подія зараз чинна" — вартий окремого зрізу з власним
   design review, не поспішного дописування в тому самому проході, що й matching.
3. **Вертикальна звірка** (сума підлеглих проти зведеного подання органу) — природно переюзає
   `repo::documents::daily_training_rollup` (Етап 7), але то окремий запуск і окрема логіка
   порівняння агрегатів, не горизонтальна пара-до-пари.
4. **Часова звірка** (нове подання суперечить попередньому БЕЗ події-пояснення) — потребує
   `submission.supersedes_id`-ланцюжка й окремого правила "остання дата без вибуття".
5. **Workflow розбіжностей** (open→notified→in_progress→resolved|dismissed, ручне закріплення
   `pinned`, нотатка розв'язання) — схема вже має всі статуси (дешево додати зараз), але UI-дії
   для них — окремий крок, коли з'явиться сенс "notified" (це прив'язано до сповіщень, §5).
6. **Сповіщення** (дзвіночок у шапці, `notification_outbox`, WhatsApp-воркер) — WhatsApp
   ЯВНО "зробити останньою" за спекою; внутрішні — після того, як є що показувати (кілька
   зрізів розбіжностей).
