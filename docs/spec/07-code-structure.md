# 07. Структура коду і карти тек

Два принципи:
1. **Перевикористовуване — у спільних теках кореня крейту** (`components/`, `widgets/`, `services/`…).
2. **Специфічне для однієї сторінки чи складеного компонента — поруч із ним** (co-location).

Плюс третій, заради економії токенів: **у кожній непорожній теці лежить коротка карта `CLAUDE.md`**
— що тут, куди класти нове. Claude Code вантажить вкладений `CLAUDE.md` автоматично, щойно агент
читає файл у цій теці, тож йому не треба робити `ls`/`grep`, щоб зорієнтуватись.

## 1. Цільова структура `app/src/`

```
app/src/
├── CLAUDE.md          карта крейту + дерево рішень "куди класти новий код" (§3)
├── lib.rs             тільки оголошення модулів
├── app.rs             shell() + App: провайдери контекстів, <Router>, нічого більше
├── routes.rs          таблиця маршрутів → pages::*
│
├── components/        UI-примітиви БЕЗ знання домену (кнопка, комбобокс, сітка, поле дати,
│                      модалка, тост, панель, шпаргалка гарячих клавіш). Не викликають server fn.
├── widgets/           ДОМЕННІ компоненти, які використовують ≥ 2 сторінки
│                      (OrgPicker, VosPicker, SubordinationTree, ActorSwitcher)
├── layout/            каркас сторінки: Header, навігація, PageFrame
├── pages/
│   ├── home/mod.rs                    проста сторінка — один файл
│   └── org_detail/                    складна сторінка — тека:
│       ├── CLAUDE.md
│       ├── mod.rs                     компонент сторінки
│       ├── server.rs                  #[server]-функції, потрібні ТІЛЬКИ цій сторінці
│       └── components/                компоненти, потрібні ТІЛЬКИ цій сторінці
│           └── name_history.rs
├── services/          #[server]-функції, які викликаються з ≥ 2 місць; по доменах:
│                      orgs.rs, subordination.rs, dictionaries.rs, health.rs …
├── types/             DTO і спільні типи, що їздять клієнт↔сервер (serde): OrgSearchResult,
│                      OrgTreeRow, Actor/Role …
├── domain/            ЧИСТА логіка без UI і БД, компілюється у WASM: normalize, dates,
│                      validation, counting (формули воронки) — з табличними тестами
├── hooks/             реактивні хелпери: use_hotkeys, use_debounced, use_actor …
├── state/             глобальні контексти (ActorContext …)
└── backend/           ЛИШЕ #[cfg(feature = "ssr")] — уся тека оголошена під cfg:
    ├── policy.rs      перевірка прав (переїжджає сюди з server/src/policy.rs — див. §5)
    ├── db.rs          дістати DatabaseConnection з контексту, транзакція + SET LOCAL app.actor
    └── repo/          SQL/SeaORM по агрегатах: orgs.rs, subordination.rs, alias.rs …
```

Стилі: **колокацію відкладено** (перевірено емпірично — [[css-colocation-deferred]]):
`cargo-leptos` не розгортає `@import` (лишає його буквальним рядком у виводі → 404 в браузері),
а крок обробки стилів виконується **до** збірки Rust-крейта `app`, тож `build.rs`-конкатенація
теж не встигає. `app/style/main.css` лишається одним файлом із секційними коментарями
("хто цей блок") замість фізичного розбиття. Переглянути, коли файл переросте орієнтир
~300 рядків (§2 правило 5) або з'явиться підтримка `@import`/pre-style хука в `cargo-leptos`.

Інші крейти:
- `server/` — тонкий: `main.rs`, `config.rs`, `db.rs` (пул), `state.rs`; пізніше — `jobs/`
  (запуск фонових задач). Доменної логіки й прав тут нема.
- `migration/` — як є.
- Майбутні важкі движки (Етап 5 — імпорт, Етап 7 — генерація документів) — **окремі крейти
  воркспейсу** (`import/`, `docgen/`) без Leptos: швидша інкрементальна збірка, менше контексту
  для агента. Ті самі правила карт.

## 2. Правила

1. **Правило двох.** Нове починається поруч із місцем використання (`pages/<p>/components/`,
   `pages/<p>/server.rs`). Коли з'являється другий споживач — **переносимо** в `widgets/`,
   `components/` або `services/` (в тому ж коміті оновлюємо обидві карти). Копіювати заборонено.
2. **Приватність сторінок забезпечує компілятор.** Модулі всередині `pages/<p>/` оголошені
   без `pub` (`mod components; mod server;`) — інша сторінка фізично не зможе їх імпортувати.
   Назовні сторінка віддає тільки свій компонент.
3. **Напрямок залежностей** (зверху вниз, ніколи навпаки):
   `pages → widgets/layout → components`; `pages/widgets → services → backend`;
   усі можуть брати `types`, `domain`, `hooks`, `state`.
   `components/` не знає домену: не імпортує `services`, `backend`, `widgets`, `pages`.
   `domain/` і `types/` не імпортують `leptos` і `sea_orm` (в `types/` допустимий `serde`).
4. **Кожна `#[server]`-функція** — тонка: `policy` → `backend::repo` → DTO. SQL у server fn не пишемо.
5. **Один публічний компонент — один файл.** Файл понад ~300 рядків → перетворити на теку-модуль
   (`combobox/mod.rs`, `combobox/keyboard.rs`, `combobox/combobox.css`).
6. **Імена**: файли й модулі `snake_case`, компоненти `PascalCase`, server fn — дієслово
   (`search_orgs`, `get_org_detail`). Теки сторінок — за маршрутом (`/orgs/:id` → `org_detail`).
7. **Тести**: юніт-тести — `mod tests` у тому ж файлі; інтеграційні з БД — `app/tests/<агрегат>.rs`;
   архітектурний тест — `app/tests/architecture.rs` (§4).

## 3. Дерево рішень "куди класти новий код" (дослівно — у `app/src/CLAUDE.md`)

1. Чиста функція без UI і БД (нормалізація, дати, валідація, підрахунки) → `domain/`
2. Тип, що передається між клієнтом і сервером → `types/`
3. SQL / SeaORM → `backend/repo/<агрегат>.rs`
4. Перевірка прав → `backend/policy.rs` (і тільки там)
5. `#[server]`-функція: для однієї сторінки → `pages/<p>/server.rs`; для ≥ 2 → `services/<домен>.rs`
6. UI-компонент, що не знає домену → `components/`
7. Доменний компонент: для однієї сторінки → `pages/<p>/components/`; для ≥ 2 → `widgets/`
8. Каркас сторінки (шапка, меню) → `layout/`
9. Реактивний хелпер → `hooks/`; глобальний контекст → `state/`
10. Нова сторінка → `pages/<p>/` + рядок у `routes.rs` + рядок у `pages/CLAUDE.md`

## 4. Карти тек (`CLAUDE.md`)

Де: у **кожній** теці коду з ≥ 2 елементами (файли/підтеки) або з неочевидним призначенням.
Сторінка з одного файлу карти не потребує. Формат — жорсткий, щоб карти були дешеві:

```markdown
# app/src/widgets — доменні компоненти, які використовують ≥ 2 сторінки

- Можна: services, components, types, domain, hooks, state. Не можна: pages, backend.
- Використовується лише однією сторінкою → назад у pages/<p>/components/.

| Елемент | Що це | Хто використовує |
|---|---|---|
| `org_picker.rs` | OrgPicker: нечіткий пошук частини з підказкою номера | pages/org_detail, pages/import |
| `subordination_tree.rs` | дерево на дату з перемикачем осі | pages/subordination, pages/home |
```

Обмеження: ≤ 40 рядків. Не більше. Жодного коду, жодного переказу реалізації — тільки
"що де лежить і куди класти нове". Якщо карта не влазить у 40 рядків — тека завелика, її треба ділити.
Кореневий `app/src/CLAUDE.md` додатково містить дерево рішень з §3 і напрямок залежностей з §2.3.
Корені `server/CLAUDE.md`, `migration/CLAUDE.md` уже є — дописати в них таблицю вмісту в тому ж форматі.

**Карти не можуть застаріти — це перевіряє тест** `app/tests/architecture.rs` (звичайний
`cargo test`, читає файли через `std::fs`):
- кожна тека в `app/src` з ≥ 2 елементами має `CLAUDE.md`;
- кожен `.rs`-файл і підтека такої теки згадані в її карті, і кожен згаданий у таблиці шлях існує;
- жодного `crate::pages::<a>` всередині `pages/<b>` (страховка поверх приватності модулів);
- `components/` не імпортує `services|backend|widgets|pages`; `domain/` і `types/` не імпортують
  `leptos|sea_orm`; `backend` оголошений під `#[cfg(feature = "ssr")]`;
- кожен `#[server]` лежить або в `services/`, або в `pages/*/server.rs`.
Падіння тесту = "онови карту / переклади файл", з назвою порушення в повідомленні.

## 5. Чому `policy` переїжджає в `app/src/backend/`

`#[server]`-функції живуть у крейті `app` (так вимагає Leptos, щоб клієнт міг їх викликати),
а `server` залежить від `app`, не навпаки. Тому `server::policy` для них недосяжний — і зараз
жодна server fn права не перевіряє (порушення жорсткого правила "права — тільки через `policy`").
У `app/src/backend/policy.rs` під `ssr` він доступний усім server fn. Крейт `server` лише
реєструє контекст (БД) і більше про права не знає.
