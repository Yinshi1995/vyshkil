# 01. Модель предметної області

Головні принципи (порушувати тільки через запис у `.claude/decisions/`):

1. **Людей поіменно не зберігаємо.** Жодних ПІБ, звань, особових номерів. Облікова одиниця —
   **група** (N військовослужбовців від частини X на навчанні Y) і **кількості**. Якщо у вхідному
   файлі є ПІБ (наприклад, файли адаптації) — при імпорті вони агрегуються в кількості й **не
   зберігаються** ні в БД, ні в логах, ні в збереженій копії файлу для повторного розбору
   (див. 03, розділ "Персональні дані").
2. **Нічого не перезаписуємо — все має історію.** Підпорядкування, назви, статуси мають періоди дії;
   кількості в групах змінюються подіями, а не апдейтом поля; будь-яке редагування йде в журнал аудиту.
3. **Два шари даних: "як подали" і "як вважаємо".** Кожне подання зберігається як є (нормалізоване),
   канонічна картина обчислюється з подань за правилами пріоритету (див. 04). Саме це дає
   динамічну звірку.
4. **Будь-яке написання → нормальна форма через довідник синонімів.** Частини, місця, ВОС, посади,
   ОВТ, курси — усе має таблицю синонімів, яка поповнюється вручну і "вчиться" з вибору користувачів.

Назви таблиць нижче — рекомендовані; типи — Postgres. Enum-подібні значення — або довідкові таблиці,
або `text` + `CHECK` (не Postgres `ENUM`, щоб додавання значення не вимагало міграції типу).

## 1. Організації та ієрархія

### `org` — будь-яка організація
Одна таблиця для всього, що може бути відправником, отримувачем, органом управління чи місцем навчання.

| Поле | Зміст |
|---|---|
| `id` | bigint identity |
| `kind` | `military_unit` (ВЧ), `command` (орган управління: АК, ОТУ, УВ(с), КСВ…), `virtual_group` (напр. ЧБП), `subunit` (батальйон/рота/взвод всередині ВЧ), `edu_institution` (навчальний заклад без номера), `company` (ТОВ/ПП), `ngo` (ГО, БФ), `foreign_state`, `other` |
| `echelon` | `text`: рота, батальйон, полк, бригада, корпус, оту, ок, ксв, … (довільна глибина, новий рівень ≠ міграція) |
| `number_kind` / `number` | `A` / `T` / `NGU` (в/ч 3070) / `null`; номер без префікса, напр. `4007`. Унікальний серед `military_unit` через частковий унікальний індекс. Порушення унікальності при імпорті — **помилка даних** (у джерелах трапляється, див. source-analysis), а не підстава створити дубль |
| `short_name` | "128 огшбр", "17 АК", "ТОВ Реактивні дрони" — поточна; історія в `org_name_history` |
| `full_name` | повна назва, якщо відома |
| `branch` | ЗСУ / НГУ / ДПСУ / … (для частин) |
| `country` | для `foreign_state` / іноземних закладів |
| `is_active`, `created_at`, `updated_at`, `deleted_at` | soft delete |

Відображення в документах: `short_name (А####)` — номер підставляється автоматично, користувач
вводить або номер, або назву, або будь-який відомий синонім.

### `org_name_history`
`org_id, short_name, valid_from, valid_to` — перейменування (напр. "брез" → "нц").

### `training_site` — місце проведення
Одна організація може мати багато місць (у А1890 — 10 населених пунктів).
`id, org_id, locality (нас. пункт, може бути null), note`. Унікальність `(org_id, locality)`.
Коли навчання на базі самої ВЧ — `training_site` цієї ВЧ з `locality = null`.

### `subordination` — підпорядкування з історією
| Поле | Зміст |
|---|---|
| `child_org_id`, `parent_org_id` | |
| `axis` | `staff` (штатне) або `operational` (оперативне) |
| `valid_from`, `valid_to` | `date`, `valid_to = null` — діє досі |
| `basis` | підстава (наказ/розпорядження), текст |
| `created_by_submission_id` | звідки дізналися |

Обмеження: для однієї `(child_org_id, axis)` періоди не перетинаються —
`EXCLUDE USING gist (child_org_id WITH =, axis WITH =, daterange(valid_from, valid_to, '[)') WITH &&)`
(потрібне розширення `btree_gist`).

Реальні приклади з даних (див. source-analysis): 142/154/61/5/92/225 з 17 АК у серпні перейшли
в 7 КШР; 110 омбр **одночасно** у звітах 17 АК (як штатна, секція "поза смугою") і 20 АК
(як оперативна). Модель мусить це виражати без хаків.

### `org_status` — статус частини в часі
`org_id, status, valid_from, valid_to, counterpart_org_id, note`, де `status`:
`in_zone` (виконує завдання в смузі УВ(с)), `out_of_zone` (у штатному підпорядкуванні нашого
органу, але завдання виконує поза смугою), `transferred` (передана іншому командуванню —
**лишається в БД**, ми відстежуємо її навчання, щоб доповісти командувачу), `disbanded`, `other`.

### `subordination_closure` — швидкість без рекурсії
Матеріалізоване транзитивне замикання: `ancestor_id, descendant_id, axis, depth, valid_from, valid_to`.
Період рядка = перетин періодів усіх ланок шляху. **Перебудовується цілком в одній транзакції**
при будь-якій зміні `subordination` (частин — тисячі, перебудова — мілісекунди; змін мало,
читань — постійно). Запит "усі підлеглі X за віссю A на дату D":
`WHERE ancestor_id = X AND axis = A AND daterange(valid_from, valid_to, '[)') @> D` — один індексний
прохід (GiST-індекс по діапазону + btree по `ancestor_id, axis`). Рекурсивні CTE в гарячих
шляхах не використовувати.

### Правило групування у звітах органу X на дату D
(звіти АК мають дві секції — див. 05)
- **Секція "основна"**: частини, у яких **оперативний** батько на D = X; плюс частини, штатно
  підлеглі X, які на D не мають оперативного батька і мають статус `in_zone`.
- **Секція "у штатному підпорядкуванні, але поза смугою / не виконують завдання в смузі"**: частини,
  штатно підлеглі X, які на D оперативно підпорядковані комусь іншому або мають статус `out_of_zone`.
- **Зведення вище (УВ(с))**: кожна частина рахується **рівно один раз** — за оперативним батьком
  (якщо є), інакше за штатним. Подвійний підрахунок 110 омбр (у 17 АК і 20 АК) — дефект, який
  тести мають ловити.
- Частини зі статусом `transferred` у зведення УВ(с) не входять, але мають окремий звіт
  "передані частини: де вчаться" (див. 05).

Ці правила — найкраща реконструкція з документів; оформи їх як одну функцію з тестами на прикладах
110 омбр і 142 омбр, щоб за потреби змінити в одному місці.

| `course` | курси без ВОС: КІБР, КІПР, КПК, СККВ, "курс лідерства середнього рівня", КПОШ, … |
| `attrition_reason` | СЗЧ; лікування/шпиталь; відрахований за станом здоров'я; не пройшов вхідний контроль; не пройшов проміжний контроль; не склав іспит; не прибув до НЦ; переведення; смерть; помилка внесення/задвоєння; інше (+текст) |
| `organizer` | хто організував/розпорядився (у даних: "20 АК", "СВ ЗСУ", "ОК ПІВДЕНЬ", "УВ «Курськ»") — посилання на `org` |

### `alias` — єдиний механізм синонімів
`id, target_type (org|site|vos|position|equipment|course|attrition_reason), target_id, raw, norm,
source (seed|manual|learned), confidence, uses_count, created_by, created_at`.

`norm` = результат **однієї** функції нормалізації (в `app`, щоб працювала і на сервері, і в WASM):
нижній регістр; латинські двійники → кирилиця (A→А, T→Т, O→О, P→Р, C→С, E→Е, K→К, M→М, H→Н, B→В, X→Х; і навпаки для
ідентифікаторів на кшталт "Vampire"); прибрати лапки всіх видів «»"“”'’, дужки, крапки, зайві
пробіли; уніфікувати дефіс/тире; "в/с"≈"вс"≈"в/сл". Порівняння — по `norm`, плюс нечіткий пошук
(`pg_trgm` similarity) для підказок.

**Навчання:** коли користувач вводить сире значення, якого нема в `alias`, і вручну вибирає
відповідність — створюється `alias(source='learned')`. Адміністратор бачить нові learned-синоніми
в окремому списку і може підтвердити/відхилити.

## 3. Групи на навчанні (ядро)

### `training_group` — канонічна група
| Поле | Зміст |
|---|---|
| `id` | |
| `sender_org_id` | хто відправив (ВЧ). **Не** підрозділ всередині — для цього `group_composition` |
| `training_kind_id`, теги `training_direction` (окрема таблиця зв'язку) | |
| `bzvp_program_id` | для БЗВП |
| `vos_id`, `position_id`, `course_id` | що саме здобувають (усі nullable: інструкторські курси без ВОС, БЗВП без ВОС) |
| `equipment_text` + зв'язок `group_equipment` | ОВТ як ввели + нормалізовані посилання |
| `site_id` | місце проведення |
| `organizer_org_id` | хто організував |
| `planned_start`, `planned_end` | `date` |
| `basis_doc_number`, `basis_doc_date` | розпорядження/наказ ("№2654/17 від 25.02.26") — окремі поля, а не в примітці |
| `inflow_source` | для адаптації: "з НЦ (ЦПП)" / "перепризначення" |
| `note` | примітка |
| `canonical_from` | яким правилом визначено (див. 04) |

### `group_composition` — розподіл за підрозділами
`group_id, subunit_org_id (nullable), subunit_label text, count`.
З рядків типу "1б тро-2\n2б тро-3\nупр-9". Валідація: сума = кількість у групі (див. 03).
Підрозділи (`org.kind = subunit`) створюються за потреби як діти ВЧ.

### `group_event` — усі зміни кількостей (event sourcing)
Кількості **не зберігаються полями** — тільки подіями.

| Поле | Зміст |
|---|---|
| `group_id` | |
| `event_type` | `planned` (план/викликали), `arrived` (прибули до НЦ), `started` (розпочали/зараховані), `added` (додані до групи, що вже вчиться), `attrition` (вибули), `completed` (завершили; прапорець `shortened` — "по скороченню"), `vos_awarded` (отримали ВОС наказом), `vos_not_awarded`, `correction` (виправлення помилки внесення/задвоєння, зі знаком) |
| `count` | int > 0 (крім `correction`, де знак значущий) |
| `reason_id` | для `attrition` / `vos_not_awarded` / `correction` |
| `occurred_on` | коли сталося (`date`) |
| `recorded_at` | коли дізналися (`timestamptz`) — **бітемпоральність** |
| `submission_id` | з якого подання |
| `award_order_number`, `award_order_date` | для `vos_awarded` |
| `note` | |

Воронка групи: `planned → arrived → started (+added) → (−attrition) → completed → vos_awarded / vos_not_awarded`.

Похідні величини (функції в одному модулі + SQL-в'юхи):
- `in_training(D)` = started + added − attrition − completed ± correction, по подіях з `occurred_on ≤ D`;
- `started_on(D)`, `completed_on(D)`, `attrition_on(D)` — події з `occurred_on = D`;
- `finishing_on(D)` — "закінчують сьогодні": групи з `completed` на D, а якщо фактичної події ще
  нема — з `planned_end = D` (позначати як прогноз);
- "як ми знали на момент T" — ті самі формули з фільтром `recorded_at ≤ T`. Потрібно, щоб
  відтворити документ, уже відправлений у минулому, і показати, що змінилося з того часу.

### `daily_counts` — матеріалізація для швидких звітів
`org_id, training_kind_id, date, in_training, started, finishing, attrition, completed` —
перераховується інкрементально при фіксації подання (тільки зачеплені org/дати).
Звіти й презентації читають звідси, а не агрегують події щоразу.

## 5. Подання, файли, аудит (деталі — у 04)

- `submission` — одна порція даних: `source_type` (`form` / `table` / `official_letter` / `scan` /
  `archive_seed`), `reporting_org_id` (хто подає), `as_of_date` ("станом на"), реквізити документа,
  `file_id`, `status` (`draft` → `parsed` → `validated` → `committed` / `rejected`), `supersedes_id`.
  Для `source_type='form'` у стані `draft` рядки сітки (ще не розібрані на `reported_*`, не пройшли
  валідацію) лежать у `draft_payload jsonb` — це буфер автозбереження (02 §6), не нормалізоване
  подання; `reported_group`/`reported_event` заповнюються при переході в `parsed`. Реквізити
  документа/`file_id` — для `table`/`official_letter`/`scan`/`archive_seed` (Етап 5+); для `form`
  лишаються `null`.
- `reported_group`, `reported_event`, `reported_staffing` — нормалізовані рядки подання **як їх
  подали**, з посиланням на канонічну сутність, до якої їх зіставлено (`matched_group_id`),
  і з оцінкою зіставлення.
- `stored_file` — метадані (`sha256`, ім'я, mime, розмір); сам файл — на диску сервера
  (`/data/files/ab/cd/<sha256>`), не в БД. Диска 7 ТБ — зберігаємо оригінали завжди
  (крім персональних даних — див. 03).
- `audit_log` — універсальний журнал: `table_name, row_id, action, before jsonb, after jsonb,
  actor, at`. Реалізація — один generic тригер Postgres на всі доменні таблиці.
- `generated_document` — кожен згенерований документ: тип, параметри, `as_of`, `knowledge_at`
  (момент, станом на який бралися дані), файл. Щоб завжди можна було показати, що саме і
  коли було доповідено.

## 6. Актор і права (без автентифікації на старті)

Автентифікації поки нема (пізніше — окремий мікросервіс, FIDO-ключі + логін/пароль).
Але **модель прав закладається з першого дня**:
- `actor` = вибрана в UI організація + роль (`admin` | `org_editor` | `viewer`); на етапі
  розробки — перемикач у шапці. Далі цю пару віддаватиме мікросервіс автентифікації.
- `admin` (замовник) редагує все.
- Решта **редагує тільки власні подання своєї організації**; корпус **не** редагує підлеглих.
- Перегляд: своя організація + її піддерево (за `subordination_closure`, обидві осі, на сьогодні).
- Уся перевірка прав — в одному модулі `policy`, який викликають усі server functions.
  Жодних перевірок прав, розкиданих по компонентах.
