# 00. Інструкція агенту: перехід на специфікацію

Досі проєкт будувався на вигаданій схемі (`unit`, `personnel`, `exercise`, `training_session`,
`metric_result`). Замовник проаналізував реальні дані й документи — справжній домен описано в
`docs/spec/`. Каркас (Axum + Leptos 0.7 + SeaORM + Postgres, mimalloc, Docker) лишається —
змінюється предметна частина і керівні файли.

**Прочитай повністю, в такому порядку:** `docs/spec/README.md` → `01-domain-model.md` →
`06-roadmap.md` → `04` → `03` → `02` → `05` → `docs/source-analysis.md`. Потім виконай Етап 0
нижче, покажи користувачу підсумок і переходь до Етапу 1 за `06-roadmap.md`.

## Етап 0. Що зробити

### 0.1. Зафіксувати поточний стан у git
У репо ще нема жодного коміту. Спершу допиши `.gitignore` (див. 0.8), потім зроби базовий коміт
поточного каркасу ("baseline: каркас Axum+Leptos+SeaORM до переходу на специфікацію"), і лише
після цього щось видаляй. Файли `*.log` у корені (`compose_up.log`, `server_run*.log`) — не комітити, прибрати.

### 0.2. Прибрати вигадану схему
`personnel` **суперечить головному принципу** (людей поіменно не зберігаємо), решта таблиць не
відповідає домену. Продакшен-даних нема — видали ці 5 міграцій і відповідні entity, перестворити
БД розробки з нуля (`taktoblik-db`: drop/create database або перестворити контейнер). Нові міграції
— з реальною датою в префіксі (`m20260927_…`), не `2024…`.

### 0.3. `CLAUDE.md` (корінь) — переписати
Тримай його коротким (≤ ~60 рядків): це те, що вантажиться в кожну сесію. Має містити:
1. Один абзац: що за застосунок (облік підготовки частин УВ(с) "Південь": форма/таблиця/звернення →
   нормалізація → звірка між рівнями → документи). Посилання: "домен — `docs/spec/README.md`".
2. **Жорсткі правила** (кожне — один рядок):
   - людей поіменно не зберігати й не логувати (тільки кількості груп);
   - жодних мережевих викликів з даними назовні (OCR, шрифти, CDN — локально); виняток — знеособлене WhatsApp-повідомлення;
   - нічого не перезаписувати без історії: періоди дії, події, `audit_log`;
   - спершу специфікація, потім код: відступ від `docs/spec` = оновити spec + рішення в `.claude/decisions/`;
   - `source_files/` — дані замовника з грифом ДСК: не комітити, не цитувати в логах, тести з ними — skip за відсутності;
   - права — тільки через модуль `policy`;
   - спільна логіка (нормалізація, парсинг дат, валідація) — в `app`, компілюється і для SSR, і для WASM.
3. Таблиця маршрутизації "питання → де дивитись" (онови існуючу): стан → `MEMORY.md`; рішення →
   `DECISIONS.md`; контракти крейтів → `INTERFACES.md`; **домен/вимоги → `docs/spec/<файл>`**
   (з коротким описом, який файл про що — можна взяти з `docs/spec/README.md`); наступний крок →
   `docs/spec/06-roadmap.md`; дані й граблі джерел → `docs/source-analysis.md`; граф коду → `cargo modules`.
4. Як запускати й перевіряти (коротко; деталі — в MEMORY.md).

### 0.4. Вкладені `CLAUDE.md` (вантажаться лише коли працюєш у цій теці)
- `migration/CLAUDE.md`: розширення `btree_gist`, `pg_trgm` (перша міграція); enum-подібні значення —
  довідкові таблиці або `text` + `CHECK`, **не** Postgres `ENUM`; кожна доменна таблиця — під generic
  тригер `audit_log`; soft delete (`deleted_at`); періоди — `valid_from/valid_to` + exclusion
  constraint; порядок реєстрації міграцій — за FK-залежностями; префікс — реальна дата.
- `app/CLAUDE.md`: все в `app` поза `#[cfg(feature = "ssr")]` мусить збиратися у WASM (без sea-orm,
  tokio, fs); нормалізація/парсинг/валідація — чисті функції з табличними тестами на реальних
  граблях із `docs/source-analysis.md`; UI-тексти українською.
- `server/CLAUDE.md`: усі server functions спершу викликають `policy`; гарячі запити по ієрархії —
  через `subordination_closure`, не рекурсивні CTE; важкі задачі (імпорт великого файлу, OCR,
  генерація pptx) — фоновими задачами з прогресом, файли обробляти потоково; RSS сервера — контролювати.

### 0.5. `.claude/settings.json` (новий, комітиться) замість `settings.local.json` для спільного
- Перенести `SessionStart` hook у `settings.json`. **Виправити команду**: `CLAUDE.md` Claude Code і так
  вантажить автоматично — не друкувати його вдруге (зайві токени щосесії). Друкувати тільки
  `.claude/memory/MEMORY.md` (стан) — і стежити, щоб він лишався коротким.
  `DECISIONS.md` у hook не потрібен — він за посиланням з `CLAUDE.md`.
- `permissions.allow` для рутинних команд: `cargo build/test/check/clippy/fmt`, `cargo leptos build`,
  `docker ps/start/logs`, `git status/diff/log/add/commit`. `permissions.deny` на читання
  `.env` і на `git push` (пушить людина).
- Великі бінарні файли (`*.pptx`, `*.pdf`, `*.zip`, `docs/templates/**`, `target/**`) — у `permissions.deny`
  для `Read`, щоб агент не тягнув їх у контекст (читати їх тільки скриптами). Перевір, чи твоя версія
  Claude Code взагалі враховує `.claudeignore`; якщо ні — видали його, щоб не вводив в оману,
  і покладайся на `permissions.deny`.
- `settings.local.json` лишити тільки для особистих PowerShell-дозволів користувача.

### 0.6. Пам'ять `.claude/memory/`
- `MEMORY.md`: **виправити хибний запис** — `source_files/` не "стороння папка з іншого інструменту",
  а дані замовника (архів старого обліку + еталонні документи), основа сідів і тестів. Секцію "Далі"
  замінити на "Етап 1 за `docs/spec/06-roadmap.md`". Прибрати згадки про CRUD для personnel тощо.
- `DECISIONS.md` + атомарні файли в `.claude/decisions/` — додати (коротко: чому, альтернативи, ціна):
  - `no-personal-data` — облік групами й кількостями; ПІБ з імпорту агрегуються і вичищаються;
  - `event-sourced-counts-bitemporal` — кількості тільки подіями, `occurred_on` + `recorded_at`;
  - `temporal-subordination-closure` — дві осі підпорядкування з історією + матеріалізоване замикання;
  - `reported-vs-canonical` — два шари даних і правило пріоритету;
  - `alias-normalization-in-app` — одна функція нормалізації для SSR і WASM + таблиця синонімів;
  - `text-enums-not-pg-enums`;
  - `depersonalized-notification-outbox` — черга сповіщень, знеособлений шаблон, канали через трейт.
  Існуючі рішення (SeaORM, mimalloc, rustls, distroless, release-профіль, cargo-modules) — лишити.
- `INTERFACES.md` — доповнювати в міру появи: `app::normalize`, `app::validation`, `app::dates`,
  `server::policy`, формат `reported_*` ↔ канон.

### 0.7. Команди й субагенти
- `.claude/commands/handoff.md` — додати крок: "якщо реалізація відступила від `docs/spec` — чи оновлено spec?"
  і "відмітити в MEMORY.md, на якому етапі roadmap ми зараз і що з критеріїв готовності виконано".
- Новий `.claude/commands/next-stage.md`: прочитати `06-roadmap.md` і MEMORY.md, визначити поточний
  етап, перелічити невиконані критерії готовності, запропонувати план найближчих кроків і чекати "ок".
- Новий субагент `.claude/agents/spec-reviewer.md` (read-only: Read, Grep, Glob, Bash для `git diff`):
  перевіряє diff проти `docs/spec` і жорстких правил — персональні дані в схемі/логах, мережеві виклики,
  обхід `policy`, перезапис без історії, рекурсивні CTE в гарячих шляхах, ENUM у міграціях.
  Викликати перед кожним комітом, що зачіпає схему, імпорт або права.
- `tidy` (haiku) — лишити як є.

## Як вести розробку далі (постійні правила)

1. **Етапами з `06-roadmap.md`**, кожен — вертикальний зріз до робочого UI. Не перескакувати етапи;
   критерії готовності — буквально як написано (там є конкретні тести на реальних прикладах).
2. **Спершу тест на реальних граблях, потім код.** Для нормалізації, дат, валідації, підрахунків,
   правил групування — табличні тести з прикладами з `docs/source-analysis.md` ("31.09",
   "545543", "A4076" латиницею, "423 обБпС", 110 омбр в двох органах, 142 омбр переходить у 7 КШР).
3. **Інтеграційні тести з БД** — окрема тестова база в тому ж контейнері Postgres, міграції з нуля
   на кожен прогін.
4. **Золоті тести документів**: після переносу архіву генерувати D1/D2 за 26.09.2026 і порівнювати
   з `source_files/Зразок/26.09/`. Якщо не збігається — спершу з'ясувати, чи це помилка в нас, чи в
   еталоні (в еталонах є ручні помилки); помилки еталонів — документувати, не підганяти.
5. **Будь-яке рішення з альтернативами** (бібліотека, підхід до pptx, OCR) — атомарний файл у
   `.claude/decisions/` + рядок у `DECISIONS.md`. Перед додаванням залежності — перевірити
   актуальність, ліцензію, підтримку і чи збирається під Windows-хост (Smart App Control уже вимкнено,
   але `cargo leptos watch` не використовувати — див. MEMORY.md).
6. **Пам'ять сервера**: 8 ГБ на все (Postgres + застосунок). Після кожного етапу — заміряти RSS
   сервера на імпорті найбільшого файлу з `source_files/` і записати в MEMORY.md.
7. **Коміти** — маленькі, по одному логічному кроку, повідомлення українською за змістом ("Етап 1:
   таблиця subordination з історією і exclusion constraint"). Перед комітом, що зачіпає схему,
   імпорт чи права — `spec-reviewer`. Не пушити (пушить людина).
8. **Коли питати людину**: якщо специфікація мовчить або суперечлива і рішення важко відкотити
   (схема, формат документа, правило звірки). Інакше — вирішити, записати рішення, рухатись далі.
9. Кінець сесії — `/handoff`. Початок нової — `/next-stage`.
