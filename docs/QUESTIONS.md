# Питання до користувача (від автономної сесії)

Автономна сесія пише сюди, коли натрапляє на рішення, яке не може прийняти сама (дані,
credential, відступ від `docs/spec`, щось що впливає на замовника) — НЕ блокує решту роботи,
переходить до наступної цілі з `docs/GOALS.md`. Користувач читає й відповідає тут-таки
(з телефону через Remote Control або з Windows), автономна сесія перевіряє цей файл на початку
кожного нового циклу й бере відповіді в роботу.

Формат одного запису:

```
## <коротко суть> (дата)
Контекст: ...
Варіанти: A) ... B) ...
Відповідь користувача: (порожньо, доки не відповів)
```

Контекст: `settings.json` містить `"Bash(git push *)"` у `deny`. /goal-критерій
"зміни закомічені й запушені в git-remote" технічно не виконуваний без зміни налаштувань.
Варіанти: A) Зняти deny-правило для push — тоді автономна сесія зможе пушити після кожного
закритого пункту. B) Лишити блок — сесія тільки комітить локально, push — руками (попередня
поведінка). **Обраний варіант (до відповіді):** B — комічу локально, відмічаю пункт закритим
після зеленого cargo test + e2e + clippy, оновлюю STATUS.md.

## Модуль авторизації: логін/пароль + FIDO2 (2026-10-01)
Контекст: Користувач просить створити модуль авторизації (логін/пароль) з підтримкою FIDO2/passkey.
Зараз актор вибирається вручну через ActorSwitcher (dev-режим, 01 §6). Spec не описує автентифікацію
детально (лише "dev-режим без автентифікації"). Потрібно розширити spec перед реалізацією.
Варіанти: A) Повноцінний auth з bcrypt/argon2 + сесії + FIDO2 WebAuthn (потребує нового spec-розділу).
B) Спрощений auth (логін/пароль, cookie-сесія) без FIDO2 — FIDO2 додати пізніше.
**Обраний варіант (до відповіді):** A — повноцінний, але спочатку spec-розділ (потрібне підтвердження).

## Пошук: PostgreSQL індекси vs Elasticsearch (2026-10-01)
Контекст: Користувач просить "проіндексуй постгрес найкращим чином чи додай Elasticsearch".
Зараз пошук org через pg_trgm (вже є індекс на alias.norm). Для 42 org це швидко. З ростом
даних (тисячі org, десятки тисяч alias) може знадобитися щось потужніше.
Варіанти: A) Оптимізувати pg_trgm індекси (GIN/GiST) — достатньо для поточного масштабу.
B) Додати Elasticsearch — окремий сервіс, складніший деплой, але потужніший full-text search.
**Обраний варіант (до відповіді):** A — pg_trgm GIN індекси (Elasticsearch зайвий для поточного масштабу).

стилізування за еталоном і без LibreOffice-перевірки верстки.
