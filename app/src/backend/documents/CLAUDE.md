# app/src/backend/documents — генератори документів (Етап 7, 05), лише байти з готових даних

- Можна: `sea-orm` НЕ можна тут — SQL живе в `backend::repo::documents`, той самий поділ, що
  `backend::import`/`repo::imports_*` (структура тут, дані вже прийшли готовим параметром).
- Кожен формат — один файл (`d1.rs`, далі `d2.rs`/`d3.rs`/`d4.rs`), як і `backend/import/`:
  реальна структура кожного документа виявилась суттєво різною (xlsx з формулами / docx-текст /
  pptx-клонування слайдів) — один "універсальний генератор" дав би неякісний код одразу під усе.
- **D1 повний тижневий файл**: 7 денних аркушів + приховані "початок"/"кінець" (маркери для
  `SUM(початок:кінець!C5)`) + "тижневий" аркуш (Закінчили/Почали за тиждень 3D-формулами).
  Параметр — `any_day_in_week` (аналогічно D2), повертає `DayLayout` для тижневого аркуша.
  Прихований `M-O`-стовпці (якщо потрібні для golden-тестів) — відкрито до зіставлення з
  `source_files/Зразок/26.09/` (docs/QUESTIONS.md — `source_files/` поки відсутні на VM).
- **D2: лише один тиждень зроблено** (не весь накопичувальний журнал за багато тижнів — те чекає
  на рішення про фонову генерацію, 05 §"Технічні рекомендації": довгий діапазон = багато SQL на
  день×корпус). Формули тут трирівневі — підсумок корпусу за день `SUM(суміжний_діапазон)` (як
  D1), але підсумок дня й підсумок тижня — суми НЕСУМІЖНИХ клітинок (`=B5+B15+...`, не
  `SUM(range)`), бо рядки-підсумки корпусів/днів розкидані поміж рядками підрозділів/днів.
  Правило групування (01 §1) тут НЕ двома секціями, як у D1 — на реальному еталоні підтверджено,
  що подвійно підпорядкований орган (`110 омбр`) просто з'являється в обох корпусах як звичайний
  рядок, без позначки "поза смугою".
